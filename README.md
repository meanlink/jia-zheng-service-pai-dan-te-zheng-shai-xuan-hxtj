# 栖里家服 · 家政服务派单特征筛选

客服登记预约并核验作业范围和入户条件，调度用历史完单筛选工时特征并发出上门交接，主管复核范围和工时偏差。已结案的回访可用于后续训练。

## 场景

栖里家服是上海一家模拟社区上门服务商。客服用电话和表格接保洁、家电清洗订单，调度为 5 位技师排班。现行流程有三个问题。证书有效期散在表格里，派单容易跨过证书到期日；客服按经验给工时，调度看不到哪些条件会拉长作业；回访原因发在群里，主管难以核对超时和预测差异。

上游输入是预约、上门作业条件、证书与已结案工时。应用接管从受理到实绩复盘的交接。下游由值班调度安排上门，由主管核对差异，已结案记录可以成为后续同品类训练样本。

| 账号 | 岗位 | 可写操作 |
|---|---|---|
| `intake` | 客服受理 · 唐宁 | 登记订单、范围补测、入户条件和到场结果，完工后登记实绩及回访 |
| `dispatch` | 值班调度 · 苏曼 | 提交模型分析，发布工时假设对照，试算并确认派工，发出或补发交接 |
| `lead` | 运营主管 · 孟慧 | 换发或续期证书，决定补测是否生效，处理派单前和回访后偏差 |

演示密码统一为 `Qili-demo-48`。三岗均可读业务页。演示数据与账号仅供本地使用。

## 启动

```sh
cp .env.example .env
docker compose up -d --build --wait
docker compose ps
```

打开 `http://127.0.0.1:18247`。后端 OpenAPI 在 `http://127.0.0.1:19247/docs`，MySQL 主机端口为 `17747`。端口默认绑定回环地址。首次创建 MySQL 卷时执行 `backend/migrations/001_dispatch.sql`。后端启动为新旧卷补齐 `002_fieldwork.sql` 中的业务表。`SEED_DEMO=true` 时后端启动自动补齐演示数据，可用 `docker compose exec -T backend python -m scripts.seed_demo` 再跑。重复执行保留订单状态、续期结果和审计。

停止开发环境用 `docker compose down`。一次性验收环境使用 `docker compose down -v --remove-orphans` 清理该项目的容器、卷和网络。

## 一天的工作剧本

1. 09:00 客服打开 `QL-1102`，沈先生预约虹口曲阳路的下午深度保洁，142 ㎡、污损 5 级、预估 75 分钟。
2. 09:04 调度在技师资质看到姚宁证书 `SH-QJ-0261` 已过期，在工作台无法选择其参与试算。
3. 09:06 调度为同单选择周兰（`SH-QJ-0186`）。worker 读取 84 条同类已结案工时样本。
4. 09:07 调度查看入选和剔除的特征、留出集误差和本单贡献，生成预测工时。预测与受理预估相差超过 30 分钟，方案进入派单前待复核。
5. 09:10 主管记录现场面积和污损核查意见，允许调度继续。调度确认时重新校验证书和预约时段。
6. 16:30 客服回访，登记追加厨房清洁后的实际分钟及原因。超出预测 30 分钟时仍需主管处理。
7. 16:40 主管核实增项并结案。工单轨迹保留两次复核、确认、回访及模型快照关联。

Seed 写入 5 位技师、5 张待办和 168 张分为两品类的合成完单，完单工时含扰动。预约和证书相对首次播种时的上海业务日生成。工作台只使用订单预约日前、同品类且已结案的历史。

## 规则与模型

- 资质检查同时看启用状态、服务品类和有效期。证书截止日含当天，必须覆盖上海业务日与预约日。分析排队、worker、试算及确认均检查。待确认方案如换证，必须重新分析。
- 一个订单只有一个当前方案，可在确认前换人重新分析。由技师行锁串行处理同日同时段的确认，已经预订的时段直接拒绝重复派单。
- 每个服务品类各有一组现行特征规则（`category_feature_rules`），新分析默认按该品类现行规则取特征。排队时把当时的规则快照写入方案；已经排队的分析即使随后启用了新规则，仍按排队时的规则计算。
- worker 按日期取最多 2,000 条记录，固定分界日留出约 20% 给验证集。特征标准化只在训练集拟合。Lasso 以固定 α=3 求解 `||y−Xw||²/(2n)+α||w||₁`，以非零系数筛选。在线性回归中用原始单位重拟合，输出保留特征的系数、验证 MAE、训练均值和 `系数 ×（本单值 − 训练均值）`。
- 预测工时等于训练均值加各特征贡献后四舍五入。以分钟记录，用 `|预测 − 受理预估|` 和 `|实绩 − 预测|` 分别决定派单前和回访后复核，默认严格大于 30 分钟才进入复核。超出历史训练范围的输入在页面中标出。
- 历史低于 30 条、日期不足以切分、无入选特征或模型共线时，worker 返回可读失败原因，方案可以重试。确认的技师经验以当时快照入账。拟合快照保存同一批历史的 SHA-256 供比对。

## 品类特征组对照与启用

特征工作台按当前待派工单的品类显示该品类的现行规则与候选对照。

1. 调度勾选一组候选特征提交对照。对照取现行规则与候选规则**同一批**已结案完单，并按**同一验证起日**切分；两次拟合的历史 SHA-256 与验证起日必须一致，否则拒绝保存。对照同时记录总体留出集 MAE 和高污损单（污损等级 ≥ 4）留出集 MAE。
2. 对照结论由这两项误差直接判定：两项都不变大才算通过；任一项变大即不通过；验证集高污损单少于 6 单则样本不足、暂缓启用。页面与接口都按记录中的误差重新判定，不采信单独写入的结论字段。
3. 只有运营主管能启用，且只能启用“通过”的对照。启用时在事务内重新核对对照所依据的现行规则仍是当前规则：若另一位主管已提交并启用了新规则，旧对照作废，须按新的现行规则重新对照后再启用，不会被静默覆盖。
4. 启用即对该品类一次性切换：写入新版本规则、停用旧版本，并记录审计（含被替换的版本与候选特征）。此后该品类新排队的分析使用新特征组；已排队的分析仍按排队快照计算。
5. 新特征组若求解失败（如未保留任何特征或共线），本次分析沿用被替换的旧规则并标注回退原因，避免整个品类失去预测。

高污损单缺样时暂缓启用。对照历史少于 30 条或无法按日期切分时，接口返回可读的失败原因。


## 代码与本地开发

| 部分 | 实现 |
|---|---|
| 页面 | `frontend/index.html`、`style.css` 和 `src/pages/`，原生 ES modules，经 Nginx `/api/` 转发 |
| 接口与鉴权 | `backend/src/app.py`、`schemas.py`、`security.py`，FastAPI、JWT HS256、Redis 登录限流 |
| 业务 | `backend/src/intake.py`、`dispatch.py`、`models.py`，MySQL 事务、状态和审计 |
| 分析 | `backend/src/feature_model.py`、`worker.py` 和 `rules.py`，scikit-learn、MySQL 持久化队列、品类特征规则版本、工作进程心跳 |
| 环境与 seed | `docker-compose.yml`、`backend/migrations/001_dispatch.sql`、`backend/scripts/seed_demo.py` |

修改 Python 后可执行 `docker compose up -d --build backend worker`。修改静态页面后重建 `frontend`。需要用宿主 Python 开发时，先起 `db` 和 `redis`，并在 `backend/` 安装依赖。API 读 `DB_HOST`、`MYSQL_PORT`、`DB_PASSWORD`、`REDIS_URL`、`JWT_SECRET`。Redis 默认只在容器网络可见，日常本地测试用 Compose 即可。`.env.example` 列出了宿主端口、MySQL 用户密码与 root 密码、JWT 签名和 seed 开关。

岗位、服务品类、预约时段、订单状态、方案状态的枚举分别见 `backend/src/models.py`、`frontend/src/domain.js` 和迁移 SQL。接口输入由 `backend/src/schemas.py` 复用 Python 枚举；状态转换由 `backend/src/dispatch.py` 执行。品类特征规则、对照与启用记录在 `backend/migrations/003_feature_rules.sql`，由 `backend/src/migrations.py` 在启动时补齐。

## 预约变更与停工

- 运营主管通过「技师停工」登记或撤销指定技师某日某时段的停工。已经确认的派工会阻止登记，停工会阻止同一时段的特征分析、试算与派单确认。
- 客服通过「上门确认与改期」登记客户确认、改期请求和新时段。待处理的改期请求会拦截派单。完成改期后，已排队或已试算的旧方案须重新分析。已派工单保留在原回访流程中。


## 派前核验、工时对照和现场交接

`QL-1105` 是罗女士在长宁天山路的上午保洁单。初始范围为 92 ㎡、污损 3 级、2 处障碍、现场有耗材，受理预估 145 分钟。

1. 08:30 主管打开「派前核验」，核对客户补发的阳台照片，批准修订为 104 ㎡、污损 4 级、3 处障碍、无现场耗材。驳回则沿用原范围。补测待复核期间暂停派单，批准后旧分析须重跑。
2. 08:35 客服确认物业完成访客报备，登记南门前台的接应安排。入户受阻时，分析排队、试算和派单确认均被拦截。
3. 08:40 调度为周兰提交特征分析，在「工时假设对照」把面积改为 180 ㎡、障碍数改为 5，保存模型版本、基准和假设工时、逐项贡献差。对照使用同一次拟合的回归系数，假设值不会写回受理工单。超出训练范围时页面标注。
4. 08:45 客服核实实际范围为 118 ㎡，提交补测。主管批准后，调度重跑拟合和试算。旧对照保留证据并标记为历史模型。
5. 08:50 调度确认派工并发出交接单。交接单保存预约、技师、预计工时、补测范围和入户条件的快照。
6. 09:05 客服登记南门未能入户。调度补发第二版，登记改由住户在东门当面接应。两版均保留。
7. 09:15 客服在第二版登记已到场。工单完工后，客服回到「派单复盘」录入工时。已发过交接单的工单需要当前版本的到场回执才能完成回访。

入户方式和核验状态、范围复核状态、到场结果写入 `backend/migrations/002_fieldwork.sql`，API 输入在 `backend/src/field_schemas.py`，页面的枚举标签在 `frontend/src/field-workspace.js` 及 `frontend/src/pages/{readiness,handover}.js`。工时对照以 `analysis_ready` 审计事件标识拟合版本，并随对应订单与方案保存；单次特征差值由 `回归系数 ×（假设值 − 原值）` 计算。模型工时和假设工时各自取整后求差。
